00.

What should I do next?

Find the row that matches where you are. Run the commands underneath. Replace feature-name with whatever describes your chunk of work.

AI'm about to start something new

Get to a clean copy of main, then branch off it.

# 1. switch to main and grab any new changes from GitHub
git checkout main
git pull

# 2. create a new branch and switch to it in one step
git checkout -b feature-name

# 3. start editing your files
Branches isolate your work. If you break something on the branch, main is unaffected.

BI'm in the middle of working

Save snapshots as you go. Each commit is a save point you can return to.

# at any time, see what's changed
git status

# save a snapshot of specific files
git add path/to/file.py another/file.md
git commit -m "Short, specific message"

# back the branch up to GitHub (first push only needs -u)
git push -u origin feature-name
# subsequent pushes are just:
git push
Commit often, push at least once a day. Each push is a backup on GitHub even if your laptop dies.

CI'm done with this chunk (solo)

Bring your branch into main. Two valid ways:

# Option 1 — merge locally, push main
git checkout main
git pull
git merge --no-ff feature-name
git push origin main

# clean up: delete the branch you just merged
git branch -d feature-name
git push origin --delete feature-name
# Option 2 — open a pull request and merge in browser
git push -u origin feature-name   # if not already pushed
gh pr create
# then click "Merge pull request" on github.com
Both end in the same state. Option 2 gives you a written record + a Merge button on GitHub. Either is fine when solo.

DSomething went wrong

Jump to When things go wrong for the full menu. Most common:

# I haven't committed yet, just want to throw it away
git restore .

# I just committed something I want to undo (keeps the changes)
git reset --soft HEAD~1

# I think I lost a commit — show me everything I've done recently
git reflog
Git almost never truly deletes a commit. git reflog is your "undo history" — it shows every move HEAD has made.
01.

Five concepts everything else builds on

Learn these five and the rest of git is just commands that move work between them.

Repository
A project tracked by git.

"My folder of code, with a built-in time machine."

Commit
A saved snapshot of files at one moment.

"A photo of the project's state, with a message about what changed."

Branch
A parallel line of commits.

"A sandbox. I can break things here without touching main."

Merge
Bringing one branch's changes into another.

"Copy what I did in the sandbox back into the real project."

Pull request
GitHub's UI for a merge — a webpage with a Merge button.

"A page that says 'merge branch X into main' with a button to do it."

The "overriding" problem

Pushing only to main moves main forward every time. If you pushed an experiment, that's what GitHub now shows. Branches fix this because your experiment lives on the branch, not on main. You decide when (and whether) the branch becomes the new main.

03.

Solo workflow — the everyday loop

For when you're the only person working on the repo. Do this every time you start a new chunk of work.

1

Start clean from main

Get the latest main from GitHub, then branch off it.

git checkout main
git pull
git checkout -b add-search-feature   # or any descriptive name
2

Edit + commit + push, repeat

Save snapshots as you go. Each commit is a save point.

git status                      # always free to run, shows the truth
git add path/to/changed-file
git commit -m "Add search box to lesson list"
git push -u origin add-search-feature  # first push of the branch
git push                        # subsequent pushes
3

When done, bring the branch into main

Switch to main, merge the branch in, push the new main to GitHub.

git checkout main
git pull                          # pick up anything new (rare when solo, free safety)
git merge --no-ff add-search-feature   # --no-ff keeps the branch visible in history
git push origin main
4

Clean up the branch

The branch did its job. Delete it locally and on GitHub.

git branch -d add-search-feature
git push origin --delete add-search-feature
Old branches clutter the list. Deleting after merge is the standard signal that the work has landed.
Variation — PR-based solo

Same flow, but step 3 becomes: git push -u origin add-search-feature → gh pr create → click Merge on GitHub. You get a written PR description and a merge commit on main with no other behavioural change.

04.

Team workflow — what's different

The branch / commit / merge model is identical. Three things are added when others are pushing alongside you.

+1Pull before you start

Always start from the latest main, because someone else may have merged since you last looked.

git checkout main
git pull   # pulls in your teammates' work
git checkout -b my-thing
If you branch off stale main, you're working on yesterday's code. Pull first, every time.

+2PR instead of local merge

Push your branch, open a PR, teammates review, then merge happens through the PR.

git push -u origin my-thing
gh pr create   # or open in browser
# review comments → push more commits → reviewers approve
# someone clicks "Merge"
The PR is the conversation. Reviewers leave comments inline, request changes, approve. The Merge button only lights up when the team is happy.

+3Update your branch with new main

If main moves while your PR is open, sync the new main into your branch.

git checkout my-thing
git fetch origin           # grab latest, don't apply yet
git merge origin/main      # bring new main into your branch
# resolve conflicts if any, commit, push
Reviewers want to merge code that already works with current main. If main moves under you, sync once before they re-review.
Merge conflicts

When two people change the same lines, git can't pick a winner. Run git status to see which files conflict, open each one, find the <<<<<<< markers, edit to the version you want, save, then git add <file> && git commit. Don't be afraid of conflicts — they're how git asks "which version is right?"

05.

Cheat sheet — by intent

Group commands by what you're trying to do. Scan the headings, not the man pages.

See what's going on

git status              # changed files, branch, ahead/behind
git log --oneline -10    # last 10 commits, one per line
git diff                # uncommitted changes (working tree)
git diff --staged         # what add'ed but not yet committed
git branch              # list local branches, * = current

Start new work

git checkout main
git pull
git checkout -b name    # create and switch in one step
git switch -c name      # modern alias for the same thing

Save progress

git add <file>          # stage specific files
git add -p                # stage in chunks, interactively
git commit -m "msg"      # save snapshot with message
git push                # back it up to GitHub
git push -u origin name # first push of a new branch

Sync with GitHub

git pull                # fetch + merge (most common)
git fetch               # fetch only, don't apply yet
git pull --rebase         # replay your commits on top of remote

Finish work — solo, local merge

git checkout main
git pull
git merge --no-ff name
git push origin main
git branch -d name
git push origin --delete name

Finish work — pull request

git push -u origin name
gh pr create            # or open github.com in browser
# click Merge on the PR page
git checkout main
git pull                # pull the merged main locally
git branch -d name      # local cleanup

Move between branches

git checkout main       # switch to main
git checkout name       # switch to existing branch
git switch name         # modern alias
git branch              # list to remember names

Inspect the past

git log --oneline --graph --all  # tree of all branches
git show <commit-sha>          # full diff of one commit
git blame <file>               # who last changed each line
git reflog                     # every move HEAD has made
06.

When things go wrong

Find the situation that matches yours. The recovery commands are safe (green), worth pausing on (amber), or destructive (red — back up first).

I haven't committed and want to throw away changes

git restore .           # discard all uncommitted changes
git restore <file>      # discard one file's changes
Safe. Only touches uncommitted changes. Already-committed work is untouched.

I just committed something I want to undo

git reset --soft HEAD~1   # undo commit, keep changes staged
git reset HEAD~1          # undo commit, keep changes unstaged
Only do this if you haven't pushed yet. The commit is gone from the branch but your edits remain.

I committed to the wrong branch

git log --oneline -5     # find the commit's sha
git checkout right-branch
git cherry-pick <sha>     # copy that commit here
git checkout wrong-branch
git reset --hard HEAD~1   # remove it from wrong branch (DESTRUCTIVE)
Only use --hard when you've confirmed the commit is safely on the other branch.

I have unsaved work and need to switch branches

git stash                # tuck changes away
git checkout other-branch
# do whatever
git checkout original-branch
git stash pop            # bring changes back
Stash is a shelf. Things you put there come back exactly how they were.

I think I lost a commit

git reflog               # every HEAD move, with sha
git checkout <sha>        # visit the "lost" state
git branch rescue <sha>   # save it as a new branch
Git almost never deletes commits. Reflog is your safety net. Anything that was ever on HEAD is recoverable for ~90 days.

I have merge conflicts

git status               # lists conflicted files
# open each file, find:
#   <<<<<<< HEAD
#   your version
#   =======
#   their version
#   >>>>>>> branch-name
# edit to the right version, remove markers, save
git add <file>
git commit               # or git merge --continue
Conflicts are a question, not an error. Git is asking "which version do you want?"

I pushed something I shouldn't have

git revert <sha>          # make a NEW commit that undoes the bad one
git push
Revert is the right tool for "I pushed it, undo it" because it doesn't rewrite history — it adds an opposite commit. Safe even after sharing.

Nuclear option — start over from GitHub

git fetch origin
git reset --hard origin/main   # wipes ALL local changes
Throws away everything local on this branch and forces it to match GitHub. Use only when you're sure nothing local is worth keeping.
Three commands that rewrite history — use with care

git reset --hard, git push --force, and git rebase can permanently lose work or break collaborators. Before running any of them on a branch others see, ask: "Did anyone else pull this?" If yes, prefer git revert instead.
